# 0006 — Spry's core on Google Cloud: a service for every piece

**Status:** accepted (Lab 9)  
**Date:** 2026-11-18

## Context

Spry runs on AWS: the site on S3 + CloudFront, the API as a container Lambda, PostgreSQL 17 on a
single RDS `db.t4g.micro` (ADR 0003), sign-in on Cognito, the weekly report on
Scheduler → SQS → Lambda → S3 → SES, and the agenda parser on Bedrock (ADR 0004). Infrastructure
is Terraform in `infra/`, applied by HCP Terraform (ADR 0005).

The question: what would it take to run the same system on Google Cloud, and what would it cost?
The goal of this step is the **core**: the site, the API and the database. Everything else is
decided below, but stays on AWS for now.

## Decision, row by row

| Spry on AWS | On Google Cloud | Decision | Why |
|---|---|---|---|
| S3 + CloudFront, static Vite site | **Firebase Hosting** | **replace** | CDN, HTTPS and a `*.web.app` certificate included, free plan. A `/api/**` rewrite to Cloud Run gives one origin and no CORS, as CloudFront did. A bare Cloud Storage bucket has no HTTPS on a custom domain without an hourly-billed load balancer. |
| Lambda + function URL (FastAPI via Mangum) | **Cloud Run** | **replace** | Runs the `runtime` target of the existing Dockerfile unchanged: the image docker compose already builds. Scales to zero, HTTPS URL included. The only code change: uvicorn listens on `$PORT`. Mangum stays in the dependencies because the AWS Lambda still uses it. |
| ECR | **Artifact Registry** | **replace** | 0.5 GB free; a cleanup policy keeps the last three images. |
| RDS PostgreSQL 17, `db.t4g.micro`, always on | **Cloud SQL for PostgreSQL 17, `db-f1-micro`, 10 GB SSD** | **replace**, stopped when not in use | See *The database*. |
| Secrets Manager (`spry/backend/database-url`) | **Secret Manager** | **replace** | The whole `DATABASE_URL` is one secret, generated by Terraform and injected by Cloud Run as an environment variable, so the app needs no Secret Manager code. 6 active versions free. |
| Cognito user pool + Google IdP | Identity Platform | **keep on AWS** (for now) | See *What does not move*. The API on Cloud Run verifies the same Cognito access tokens; Cognito just allows the `*.web.app` origin. |
| EventBridge Scheduler → SQS → builder Lambda → S3 → mailer Lambda | Cloud Scheduler → Pub/Sub or Cloud Tasks → Cloud Run → Cloud Storage | **keep on AWS** (stretch) | Works, holds every past report, and is free at this volume on both sides. |
| SES | no Google service | **keep SES** | See *E-mail*. |
| Bedrock (Mistral Large 3) | Vertex AI (Gemini, Claude/Mistral through Model Garden) | **keep on AWS** (stretch: compare) | Trial credit does not pay for partner models; the parser has its own function URL and does not care where the site lives. |
| Lambda IAM role | **Service account `spry-api`** | **replace** | One identity per program: `spry-terraform` deploys, `spry-api` runs. `spry-api` has Cloud SQL Client and access to its one secret, nothing else. The default compute account (Editor) is not used. |
| CloudWatch Logs | **Cloud Logging** | **replace** | Automatic for Cloud Run; free allotment covers a lab. |
| HCP Terraform + AWS dynamic credentials | **HCP Terraform workspace `spry-gcp`** + GCP dynamic credentials | **replace** | Separate workspace and state (`gcp/`): one plan can never touch both clouds. HCP Terraform authenticates through Workload Identity Federation; no service account key exists. |
| GitHub Actions → AWS via OIDC | GitHub Actions → GCP via Workload Identity Federation | **prepared** (stretch) | The GitHub provider is in `gcp/bootstrap`, admitting only repository id `1399786735` of owner id `259185571`. |

## The database

| Option | Latency | Bill (a month) | Code |
|---|---|---|---|
| Cloud SQL `db-f1-micro`, 24/7 | ~1 ms, same region as Cloud Run | $7.67 compute + $1.70 disk = **$9.37** | none, same PostgreSQL 17, same Alembic migrations |
| **Cloud SQL, stopped outside use** (chosen) | same, plus ~1–2 min to start it | **$1.70** idle; +$0.0105 per running hour | none |
| Firestore | ~10 ms per read, no joins | **$0** at student traffic; grows with reads (see `docs/gcp-answers.md`) | rewrite models, queries, attachments (ADR 0002 keeps files in Postgres; Firestore documents stop at 1 MiB), and migrations |
| Keep RDS on AWS, call it from Cloud Run | ~25–35 ms per query us-central1 → us-east-1, a list page does several | $14 RDS stays + egress both ways | none, but RDS is private (ADR 0003): it would need a public endpoint or a VPN, both worse than either cloud alone |

**Chosen:** Cloud SQL, `db-f1-micro`, `ENTERPRISE` edition (shared-core tiers do not exist in
Enterprise Plus), 10 GB SSD, no backups, public IP with **no authorised networks** and
`ENCRYPTED_ONLY`: nothing can reach it except through the Cloud SQL connector, which checks IAM.
Cloud Run mounts the connector as a Unix socket (`/cloudsql/<connection name>`), so no VPC,
Serverless VPC Access connector or private IP range is needed. `db_activation_policy` in
`gcp/terraform.tfvars` is the switch: `NEVER` stops it, `ALWAYS` starts it.

Pooling: one Cloud Run instance at most (`api_max_instances = 1`); SQLAlchemy's default pool
(5 + 10 overflow) stays under the ~25 connections `db-f1-micro` allows. On Lambda pooling was
off because Aurora could not pause otherwise; Cloud SQL never pauses, so that reason is gone.

**Data:** migrations run against the empty database (the entrypoint runs `alembic upgrade head`
on each start). Not `pg_dump` from RDS: RDS is in private subnets with no bastion, and the AWS
copy keeps serving. Meetings are per user (Cognito `sub`), and the sub is the same on both clouds,
so a dump could be imported later without changes.

Firestore is the right answer if the app must cost $0 while idle *and* the data model is simple.
Spry has relations (meetings → attachments), bytea attachments and Alembic migrations;
rewriting all of that to save $1.70 a month (with the instance stopped) is a bad trade.

## E-mail

Keep **SES**. The domain `spry.pp.ua` is verified with DKIM, the sandbox exit is done, and the
weekly report stays on AWS anyway. If the mailer moves to Cloud Run later, it calls SES with
**no stored AWS key**: an IAM role on AWS trusts Google's OIDC issuer (`accounts.google.com`)
for the `spry-api` service account's unique id, and the container exchanges its Google ID token
with `sts:AssumeRoleWithWebIdentity`, the mirror of what Workload Identity Federation does in
the other direction. The fallback, a provider such as Mailgun or SendGrid, would put its API key
in **Secret Manager** as a second secret, read by the mailer's service account only.

## What does not move, and why

- **Sign-in (Cognito).** Cognito does not export password hashes. Moving users to Identity
  Platform means every e-mail/password user resets their password, and Google users are
  re-linked. Its free tier (50,000 MAU) beats Cognito's 10,000, which matters to nobody at
  Spry's size. The API checks tokens from either pool equally easily, so this is the cheapest
  piece to leave where it is.
- **The weekly report.** Past reports live in S3, the mail goes through SES, and the pipeline
  costs nothing on AWS. Moving it is rebuilding five resources to produce the same CSV.
- **The agenda parser.** Mistral on Bedrock is chosen and evaluated (ADR 0004,
  `docs/agenda-parser-answers.md`). Partner models on Vertex are not covered by the trial
  credit. Gemini is the comparison worth doing (stretch), not a migration.

## Consequences

- Two clouds serve the same site: `app.spry.pp.ua` (AWS) and `spry-anastasiia-2026.web.app`
  (GCP), each with its own database. Sign-in and the parser are shared, on AWS. `infra/` lists
  the Firebase origin in `extra_site_origins` (Cognito callbacks) and `allowed_origins`
  (parser CORS).
- The image is shared; only the entry point differs (`lambda` target on AWS, `runtime` on GCP).
- Cold starts on Cloud Run include `alembic upgrade head`, about a second. Fine for a lab; a
  team would run migrations as a Cloud Run job in the deploy instead.
- The Cloud SQL instance bills by the hour until stopped. `make gcp-db-stop`, or
  `db_activation_policy = "NEVER"` and an apply, or `make gcp-destroy`.
